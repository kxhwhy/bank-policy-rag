存储层 三个存储各司其职，职责不重叠
MySQL · bank_policy
唯一事实源。存 documents（文号/状态/施行日/替代关系） 与 clauses（条文/章节/业务条线）。
为什么在这里：效力判断要结构化字段，向量库只有文本
Milvus · policy_clause
稠密 1024 维 + 稀疏倒排双索引，标量字段支持按业务条线过滤。 只负责"找得到"，不负责"能不能用"。
为什么在这里：MySQL 做不了语义相似度检索
Redis · db3
问答结果缓存，TTL 24h。与 Milvus 元数据的 db0 隔离，键前缀 policy_qa: 不冲突。
为什么在这里：同一问题重复问不必重跑全链路
模型层 三个模型，各管一段
BGE-M3 · 本地 2.2G
一次推理同时产出稠密与稀疏向量，入库与召回共用同一模型，保证向量空间一致
bge-reranker-large · 本地 2.1G
交叉编码器逐对打分，把"整体相似"和"能回答问题"区分开
DeepSeek-chat · 远程
生成答案与策略兜底判定；temperature 0.1 压低发挥空间，减少编造
离线入库 在线问答 检索与校验 缓存 模型与策略
设计主线：三层降级，任一层失效都不阻断问答。 缓存不可用 → 照常走全链路；重排不可用 → 退回向量排序；模型不可用 → 降级为条款直读并明示； 向量召回为空或全低于阈值 → 拒答而不是编。 每一处降级都在页面上可见，不静默降级。
